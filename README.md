# antigravity-acp

[English](README.en.md)

**تعليمة نصية تدخل — كود منفَّذ ومُتحقَّق منه برمز خروج حقيقي يطلع.**

محوّل Agent Client Protocol (ACP) بلغة TypeScript: 21,029 سطر مصدر، و 533 حالة اختبار في 69 ملفاً.

يحوّل أداة CLI إلى وكيل برمجي فرعي داخل أي محرر يدعم ACP. فوقه طبقة تنسيق تشغّل عدة وكلاء بالتوازي، وطبقة تحقّق لا تصدّق ادّعاء الوكيل. يُبنى ويُختبر على Windows و Ubuntu في CI عند كل دفعة.

---

## المشكلة

الوكيل البرمجي يكتب «تحققت، الاختبارات تنجح». هذه جملة نصية، لا دليل. النموذج يولّد الجملة نفسها سواء نجح الأمر أو فشل.

ثلاث مشاكل عملية:

1. ادّعاء بلا إثبات. لا أحد يشغّل أمر البناء فعلاً.
2. مهمة واحدة في كل مرة. بقية نوى المعالج معطّلة.
3. مهمة تحليل تنتهي بتعديل ملفات لم يُطلب تعديلها.

هذه الأداة تعالج الثلاث.

## كيف يشتغل

| المكوّن | الوظيفة |
|---|---|
| المحوّل | كل دور محادثة ACP يصبح تشغيلة CLI واحدة، تُبثّ كـ tool call، وتُلغى عبر `session/cancel` |
| `delegate` | مهمة واحدة، عارض حيّ في المتصفح، وملخّص مضغوط بدل البثّ الكامل |
| `fanout` | مهام مستقلة بالتوازي، كل مهمة في نسخة عمل معزولة (git worktree مع `--worktree`) |
| `swarm` | هدف واحد يُقسَّم: مخطِّط يوزّع ملفات متفرّقة ← تنفيذ متوازٍ ← تحقّق ← إصلاحة واحدة |
| `capacity` | يقيس ذاكرة تشغيلة حقيقية، ويوصي بعدد الوكلاء المتوازين لهذا الجهاز |
| `verify` | يشغّل أمر البناء أو الاختبار، ويقرأ رمز الخروج |

## أهم قرار في التصميم

### 1. التحقق يقرأ رمز الخروج، لا كلام الوكيل

**المشكلة:** الوكيل يكتب كلمة «verified» في نصّه دون أن يشغّل شيئاً.

**القرار:** المحوّل نفسه يشغّل أمر التحقق كعملية فرعية، ويطبع رمز خروجها الحقيقي في سطر `verified: true (exit 0)`. المهلة 180 ثانية، ويُحتفظ بآخر 40,000 حرف من المخرجات.

**العائد:** بعد فشل الأمر نفسه مرتين متتاليتين، يُطبع `ESCALATE` بدل محاولة ثالثة عمياء. **التكلفة:** زمن أمر البناء مرة واحدة لكل مهمة.

### 2. «القراءة فقط» تُنفَّذ بلقطة واستعادة

**المشكلة:** الوكيل الفرعي يكتب على القرص. جملة «لا تعدّل شيئاً» توجيه، لا ضمان.

**القرار:** قبل مهمة التحليل تُؤخذ لقطة لشجرة الملفات، وبعدها تُستعاد. كل ملف تغيّر يُرجَع، وكل ملف جديد يُحذف.

**الحدود المقيسة:** 5,000 ملف، 4 ميغابايت للملف الواحد، 80 ميغابايت إجمالاً. اللقطة تتخطى `.git` و `node_modules` و `dist`. فوق الحدّ تُلغى اللقطة بدل إعطاء ضمان كاذب.

### 3. حارس ملفات الإعداد

**المشكلة:** أسرع طريقة لجعل الاختبار ينجح هي تعديل ملف الإعداد، لا إصلاح الكود.

**القرار:** بعد كل مهمة يقارن المحوّل الملفات المتغيّرة بستة أسماء إعداد مراقبة، منها `tsconfig.json` و `.eslintrc*` و `.acp-verify`، وبثلاثة حقول حسّاسة في `package.json`: `eslintConfig` و `scripts.lint` و `scripts.test`.

إن تغيّر أحدها دون ذكره في نص المهمة، يُطبع `config_tamper: BLOCKED` ولا يُعتمد التحقق.

## التشغيل

يحتاج Node.js 20 أو أحدث، وأداة CLI للوكيل مثبَّتة ومسجَّل دخولها.

```bash
npm ci && npm run build
acp init .
acp "أضف مسار /health واختباراً له" --verify "npm test"
```

| الخيار | الأثر |
|---|---|
| `--verify "<cmd>"` | المحوّل يشغّل الأمر ويطبع رمز خروجه. الفشل يجعل خروج البرنامج غير صفري |
| `--read-only` | لقطة واستعادة: أي ملف يكتبه الوكيل يُرجَع |
| `--session <name>` | جلسة دائمة لكل مشروع؛ التعديل التالي يستأنف نفس المحادثة |
| `--json` | نتيجة مهيكلة: الملفات، الأدوات، الملخّص، التحقق، الزمن |

مقتطف من المخرج بعد انتهاء المهمة:

```
===== ACP-DELEGATE-RESULT =====
status: ok
session: main (resumed · pinned)
stopReason: end_turn
elapsed: 14.2s
files_touched: server.js, server.test.js
tool_calls: 2
verified: true (exit 0)
scope: ok
viewer: http://127.0.0.1:57868
===============================
```

السطران المهمّان هما `verified` و `scope`. الأول رمز خروج حقيقي، والثاني يقارن الملفات المتغيّرة بالملفات التي أعلن الوكيل أنه لمسها.

## لماذا بنيته

أعمل مشرف تقنية معلومات، وأدير مهام برمجية متوازية؛ الأداة تشغّل افتراضياً وكيلاً واحداً لكل نواتين من المعالج.

كنت أراجع ادّعاءات لم يقسها أحد، فبنيت طبقة تقرأ رمز الخروج بدلاً عني.
