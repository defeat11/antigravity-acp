# antigravity-acp

[English](README.en.md)

**تكتب تعليمة نصية، ويطلع لك كود منفَّذ ومتحقَّق منه برمز خروج حقيقي.**

محوّل Agent Client Protocol (ACP) مكتوب بـ TypeScript: 21,029 سطر مصدر، و 533 حالة اختبار في 69 ملفاً.

ياخذ أداة CLI ويخليها وكيل فرعي داخل أي محرر يدعم ACP. فوقها طبقة تنسيق تشغّل عدة وكلاء بنفس الوقت، وطبقة تحقّق ما تصدّق كلام الوكيل. يُبنى ويُختبر على Windows و Ubuntu في CI مع كل push.

---

## المشكلة

الوكيل يكتب لك «تحققت، الاختبارات تنجح». هذي جملة، مو دليل. النموذج يطلّعها نفسها سواء نجح الأمر أو فشل.

ثلاث مشاكل تجيك بالشغل:

1. ادّعاء بلا دليل. ما فيه أحد يشغّل أمر البناء أصلاً.
2. مهمة وحدة كل مرة. باقي نوى المعالج فاضية.
3. مهمة تحليل تخلص وهي معدّلة ملفات ما أحد طلب تعديلها.

الأداة هذي تعالج الثلاث.

## كيف يشتغل

| المكوّن | الوظيفة |
|---|---|
| المحوّل | كل دور محادثة في ACP يصير تشغيلة CLI وحدة، تنعرض كـ tool call، وتوقفها بـ `session/cancel` |
| `delegate` | مهمة وحدة، عارض حيّ بالمتصفح، وملخّص قصير بدل ما يرمي لك المخرجات كلها |
| `fanout` | مهام مستقلة تشتغل بنفس الوقت، كل مهمة في نسخة عمل لحالها (git worktree مع `--worktree`) |
| `swarm` | هدف واحد ينقسم: مخطِّط يوزّع ملفات ما تتقاطع ← تنفيذ بالتوازي ← تحقّق ← جولة إصلاح وحدة |
| `capacity` | يقيس ذاكرة تشغيلة حقيقية، ويقول لك كم وكيل يتحمّل جهازك بنفس الوقت |
| `verify` | يشغّل أمر البناء أو الاختبار، ويقرأ رمز الخروج |

## أهم قرار في التصميم

### 1. التحقق يقرأ رمز الخروج، لا كلام الوكيل

**المشكلة:** الوكيل يكتب كلمة «verified» في رده وهو ما شغّل شي.

**القرار:** المحوّل هو اللي يشغّل أمر التحقق كعملية فرعية، ويطبع رمز خروجها الحقيقي في سطر `verified: true (exit 0)`. المهلة 180 ثانية، ويحتفظ بآخر 40,000 حرف من المخرجات.

**العائد:** لو فشل نفس الأمر مرتين ورا بعض، يطبع `ESCALATE` بدل محاولة ثالثة عمياء. **التكلفة:** وقت أمر البناء مرة وحدة لكل مهمة.

### 2. «القراءة فقط» تُنفَّذ بلقطة واستعادة

**المشكلة:** الوكيل الفرعي يكتب على القرص. جملة «لا تعدّل شيئاً» كلام، مو ضمان.

**القرار:** قبل مهمة التحليل ياخذ لقطة لشجرة الملفات، وبعدها يرجّعها. أي ملف تغيّر يرجع مثل ما كان، وأي ملف جديد ينحذف.

**الحدود المقيسة:** 5,000 ملف، 4 ميغابايت للملف الواحد، 80 ميغابايت للكل. اللقطة تتجاوز `.git` و `node_modules` و `dist`. لو زاد عن الحدّ، تُلغى اللقطة بدل ما تعطيك ضماناً كاذباً.

### 3. حارس ملفات الإعداد

**المشكلة:** أسرع طريقة تخلي الاختبار ينجح هي إنك تعدّل ملف الإعداد، مو إنك تصلح الكود.

**القرار:** بعد كل مهمة يقارن المحوّل الملفات المتغيّرة بستة أسماء إعداد مراقَبة، منها `tsconfig.json` و `.eslintrc*` و `.acp-verify`، وبثلاثة حقول حسّاسة في `package.json`: `eslintConfig` و `scripts.lint` و `scripts.test`.

لو تغيّر واحد منها وما كان مذكوراً في نص المهمة، يطبع `config_tamper: BLOCKED` وما يعتمد التحقق.

## التشغيل

يبي لك Node.js 20 أو أحدث، وأداة CLI للوكيل مثبّتة ومسجّل فيها دخولك.

```bash
npm ci && npm run build
acp init .
acp "أضف مسار /health واختباراً له" --verify "npm test"
```

| الخيار | الأثر |
|---|---|
| `--verify "<cmd>"` | المحوّل يشغّل الأمر ويطبع رمز خروجه. لو فشل، يطلع البرنامج برمز غير صفري |
| `--read-only` | لقطة واستعادة: أي ملف يكتبه الوكيل يرجع مثل ما كان |
| `--session <name>` | جلسة ثابتة لكل مشروع؛ التعديل الجاي يكمّل نفس المحادثة |
| `--json` | نتيجة مهيكلة: الملفات، الأدوات، الملخّص، التحقق، الوقت |

شكل المخرج بعد ما تخلص المهمة:

```
===== ACP-DELEGATE-RESULT =====
status: ok
session: main (resumed · pinned)
stopReason: end_turn
elapsed: 14.2s
files_touched: server.js, server.test.js
tool_calls: 2
verified: true (exit 0)
scope: ok
viewer: http://127.0.0.1:57868
===============================
```

أهم سطرين هما `verified` و `scope`. الأول رمز خروج حقيقي، والثاني يقارن الملفات اللي تغيّرت بالملفات اللي قال الوكيل إنه لمسها.

## لماذا بنيته

أشتغل مشرف تقنية معلومات، وأدير مهام برمجية بنفس الوقت؛ الأداة تشغّل افتراضياً وكيلاً واحداً لكل نواتين من المعالج.

كنت أراجع ادّعاءات ما قاسها أحد، فبنيت طبقة تقرأ رمز الخروج بدالي.
